# LV2 数据迁移：7z 归档 → Parquet 列存

本文回答三个问题：**当前用的是什么数据**、**能否改成 Parquet 列存+压缩并按月/周分区**、
以及**迁移前后如何对比**。所有结论都来自本仓库内的实测脚本，可复现。

## 结论速览

| 问题 | 答案 |
|---|---|
| 用的是什么数据 | 万得 Level-2 逐笔（行情快照 + 逐笔委托 + 逐笔成交），59 个交易日、59 个 7z 归档、318 GB；单日约 47.6 GB / 7,900 只 / 6.1 亿行 |
| 能上 Parquet 吗 | **能。** zstd-3 + 字典编码达 **10.09x**（相对 CSV），比原 7z 归档还小 **1.14x** |
| 能按月/周分区吗 | **能，已实现并验证。** `--freq month` / `--freq week`，目录形如 `month/month=2026-07/date=20260731/`；周分区实测 `week/week=2026-W27/date=20260630/` |
| 结果是否一致 | 逐字段指纹 **33/33 PASS**；随机 120 只跨 78 个代码分组 **120/120 一致**；全 59 天全列越界扫描 **异常 0**；HTTP **22/22 OK** |
| 唯一的行为变化 | 市价委托的 `-1.00` 元哨兵价格被正确还原。旧实现在这类股票上 `OverflowError` → **HTTP 500 永久不可读**；新实现可读 |
| 性能 | 首次访问 0.51 s → **0.206–0.244 s（约 2.1x）**；`daily_kline` 快 **97–590x**（HTTP `/api/daily` 47,085 ms → 140 ms）。Parquet 放在慢盘上优势会消失，见 5.3 |
| 磁盘 | 每「股票×日」额外占用 3.96 MB → **0.62 MB（6.4x）** |
| 已转换 | **59 / 59** 个交易日，278.12 GB，覆盖 4 个月分区 |
| 存放位置 | **Parquet 在 C: 的 `hfq/data-parquet`**（快盘，冷加载 0.235 s）；**7z 归档在 `D:\data-lv2`**。两者位置都可用环境变量覆盖 |
| 总成本 | 约 **9.5 小时**（单日中位 9.7 分钟）；归档按你的要求全部保留 |

## 1. 你在用什么数据

### 1.1 来源与形态

`hfq/data-lv2/*.7z` —— 万得（Wind）Level-2 逐笔行情，**每个交易日一个 7z 归档**。

| 项目 | 值 |
|---|---|
| 归档数 | 59 个（`20260630` … `20260921`） |
| 归档总体积 | 318.19 GB |
| 单日解压后 | 45.9 GB（`20260901` 实测 45.91 GB） |
| 单日标的数 | 7,895 只（含 SZ/SH 个股、基金、债券） |
| 全样本 universe | 9,143 个代码（跨 59 日并集） |
| 归档格式 | 7z **solid** 压缩，单日 3,211 个块，23,685 个成员文件 |
| 编码 | GBK CSV（表头中文，数据行纯 ASCII） |

### 1.2 每只股票三个 CSV

| 文件 | 列数 | 内容 | 单日行数（20260901） |
|---|---|---|---|
| `行情.csv` | 67 | 十档盘口快照序列（约 3 秒一帧） | 28,863,782 |
| `逐笔委托.csv` | 11 | 逐笔委托（上交所撤单也在其中，`A`=新增/`D`=撤单） | 335,785,379 |
| `逐笔成交.csv` | 13 | 逐笔成交（深交所撤单以成交代码 `C` 标记） | 217,950,050 |

约定：价格为**元 × 10000** 的整数，时间为 `HHMMSSmmm`。深交所的「交易所委托号」与
「成交编号」共享同一个 ApplSeqNum 序列，合并后按 `aseq` 排序即得逐笔主表的精确时序。

### 1.3 上层怎么消费

- `hfq/app/data.py` 把三份 CSV 解析成**统一的逐笔事件流**（委托/成交/撤单），
  再派生 `orders_summary`（逐笔委托聚合）、`basic`（当日 OHLC/涨幅/涨跌停）、
  十档盘口、分时、委托阶梯、区间统计等。
- `hfq/server.py` 提供 16 个 JSON 接口。
- `predictor/ambush/strategy.py` 也用同一批归档做选股/回测（独立的一套抽取逻辑）。

### 1.4 原读取路径的痛点

1. **solid 归档的随机访问代价高**：取 1 只股票要把途经的压缩块整体解压。
2. **同一份数据被反复落盘**：抽出的 CSV 永久留在 `cache/<date>/<code>/`
   （2.5 MB/只），再叠一份二进制缓存 `_cache_vN.bin`（1.46 MB/只）。
   每只股票看一次就多占约 **3.96 MB**。
3. **跨日查询退化成逐日全量解析**：`daily_kline` 要逐日把当日行情重新派生一遍。
4. `py7zr` 的选择性解压存在偶发 `Bad7zFile: Specified path is bad`（实测复现到
   原实现上），调用链没有重试。

实测基线（`scripts/bench_baseline.py`，`000001.SZ` / `20260901`）：

| 场景 | 耗时 |
|---|---|
| 7z 打开+列目录（建索引） | 347 ms |
| 从 solid 归档抽 1 只股票 | 353 ms |
| 解析 3 份 GBK CSV | 1,559 ms |
| **冷访问合计** | **1,912 ms** |
| 命中 `_cache_v1.bin` | 286 ms |

## 2. 能不能用 Parquet 列存 + 压缩，按月/周分区

**可以，而且比 7z 还小。** 结论来自实测，不是估算。

### 2.1 压缩率：zstd-3 追平并超过 7z

LZMA 在 solid 流上很强（45.91 GB → 5.14 GB，8.93x），但 CSV 的冗余主要在
**每行重复的代码/日期/逗号文本**。改成整数列 + 字典编码后，这部分冗余本来就消失了。

样本实测（`scripts/bench_parquet.py`、`bench_encoding.py`）：

| 编码 | 逐笔委托 | 逐笔成交 |
|---|---|---|
| snappy | 5.19x | 4.46x |
| **zstd-3 + 字典** | **12.39x** | **9.28x** |
| zstd-9 | 12.85x | 9.58x |
| gzip-6 | 11.33x | 8.80x |
| 显式 DELTA_BINARY_PACKED | 8.35x（**更差**） | — |

> delta 编码对序号列反而更差：这些列低基数、字典+zstd 已经吃掉冗余，delta 破坏了
> 跨行重复。最终选择 **zstd level 3 + 对字符串列开字典**。

全天实测（全量 59 天合计）：

| | 体积 | 相对 CSV | 相对 7z |
|---|---|---|---|
| CSV（解压后） | 2805.71 GB | 1.00x | 8.82x |
| 7z 归档 | 318.19 GB | 8.82x | 1.00x |
| **Parquet** | **278.12 GB** | **10.09x** | **1.14x（更小）** |

单日平均：CSV 47.55 GB → Parquet **4.71 GB**。

### 2.2 分区：按月/周，日内再按 date + code 分片

```
data-parquet/
├── _meta/manifest.json                       schema 版本、分区频率、universe、分片参数
├── _meta/codes/<YYYYMMDD>.parquet             当日标的清单
├── month/                                    ← 分区族目录（--freq 决定，可 month 或 week）
│   └── month=2026-07/                        ← 一级分区（按周时为 week=2026-W31）
│       └── date=20260731/                    ← 二级分区
│           ├── orders-000.parquet … orders-035.parquet
│           ├── trades-000.parquet …
│           └── quotes-000.parquet …
├── month/month=2026-09/date=20260901/…
└── catalog/month/month=2026-09/catalog-<date>.parquet   日线目录（跨日 K 线一次扫完）
```

已建成的数据集覆盖三个不同月份，可直接看到分区落地：

| 交易日 | 分区目录（相对 `data-parquet/`） | 体积 |
|---|---|---|
| `20260630` | `month/month=2026-06/date=20260630/` | 5.27 GB |
| `20260731` | `month/month=2026-07/date=20260731/` | 5.08 GB |
| `20260901` | `month/month=2026-09/date=20260901/` | 4.49 GB |

全量 59 天的单日体积区间为 **3.56 – 5.88 GB**（均值 4.71 GB）。

周分区同样验证过（`--freq week`）：

```
week/week=2026-W27/date=20260630/
week/week=2026-W36/date=20260901/
```

- **一级分区 = 月或周**（`--freq month|week`），决定目录边界，按时间范围查询只碰
  对应目录。
- **二级 `date=`** 让「某一天」直接定位到目录，也让增量追加天然幂等。
- **文件分片按 universe 序号每 256 只一个文件**，分片号由 code 在 universe 中的位置
  整除得到，**跨交易日稳定**。因此按 code 查询只需打开 1 个文件，再靠 row-group 的
  min/max 统计剪枝。

### 2.3 剪枝粒度：row_group_size=65536

分片内按 code 升序写入，row group 大小决定「为取一只股票要解压多少」。

| rows/row-group | 文件体积 | 单股票过滤读（orders/trades/quotes） |
|---|---|---|
| 262,144 | 16.5 MB | 15.7 / 18.7 / 24.7 ms |
| **65,536** | **16.5 MB** | **6.9 / 8.3 / 11.4 ms** |
| 32,768 | 16.6 MB | 6.2 / 6.3 / 7.4 ms |
| 16,384 | 16.7 MB | 8.1 / 7.8 / 8.3 ms |

体积几乎不变，读却快一倍；再往下 row-group 数量过多，footer 统计扫描反而拖慢
（102 MB 的分片上 32k → 18.5 ms、16k → 30 ms）。取 **65,536**。

### 2.4 只存应用真正消费的列

`行情.csv` 的 67 列里，`data.py` 只用 8 个标量 + 40 个阶梯格。刻意**不存**
第 5/6 列（成交量/成交额 增量）和 57–60 列（加权叫价、叫卖/叫买总量）：这些列应用
从不读取，且 `16xxxx.SZ` 基金在首帧写入了越界值，见 2.6。

### 2.5 价格/数量用 int64，不用 int32

实测 `20260731` 存在 `委托价格 = 9,999,990,000`（元×10000，即 999,999 元级报价）
与 `申买量1 = 2,203,394,970`（22 亿股级挂单），**都超出 int32**。

加宽到 int64 的代价实测只有 **3%**（15 个分片合计 737.3 MB → 761.1 MB）：

| | int32 | int64 | 比例 |
|---|---|---|---|
| orders | 91.58 MB | 96.11 MB | 1.05x |
| trades | 120.44 MB | 123.88 MB | 1.03x |
| quotes | 26.00 MB | 27.32 MB | 1.05x |

因为高位字节全 0，zstd 几乎不额外付费。所以价格/数量一律 int64。

### 2.6 源数据质量问题与处置

迁移过程中在原始 CSV 里发现三类越界值，都只在少数标的的个别行出现：

| 现象 | 出现位置 | 旧实现的表现 | 处置 |
|---|---|---|---|
| `2^64 - n` 形式的成交量/成交额 | `16xxxx.SZ` 基金 `行情.csv` 首帧（`20260901` 共 108 个文件、245 处） | 应用不读这两列 | **不收录该 2 列** |
| `2^64 - 10000` 形式的委托价格 | 市价委托行（`20260731` 有 7 只） | 解析成 `1.844674407370954e15` 元，随后 `_encode_stock` 的 `array.array("i")`（int32）**抛 OverflowError，该股票永久不可读** | **按二补码还原为 -1.00 元** |
| 合法但超 int32 的大额报价/挂单 | 每个交易日 1–2 只（如 `20260630/001399.SZ`、`20260901/301697.SZ`） | 同样 `OverflowError`，该股票永久不可读 | **int64 容纳** |

> 关键点：后两类**不是行为差异，而是修复了旧实现的一个真 bug**。旧代码在写二进制
> 缓存时把价格塞进 `array.array("i")`，任何超 int32 的值都会让 `StockData()`
> 直接抛异常；`_save_binary` 只捕获 `OSError`，所以异常一路冒到 HTTP 层。
> 实测 `20260731` 的 7 只哨兵股票在旧实现下**全部崩溃**，新实现全部可读。

实现上，整数列统一按 **uint64** 解析（两种写法都装得下），再用
`astype(int64)` 按二补码还原，因此不需要任何逐行特判。
`scripts/verify_sentinel.py` 专门验证该差异的性质；
`scripts/scan_old_overflow.py` 统计「旧实现会崩溃」的标的数。

| `hfq/scripts/bench_*.py`、`verify_*.py`、`scan_*.py`、`smoke_http.py` | **新增**。基准、校验与诊断 |

### 4.1 后台转换期间的可用性

数据集是逐日追加的，所以：

- **manifest 热重载**：`Store.maybe_reload()` 在 manifest 的 mtime 变化时重载（默认
  5 秒节流），由 `data.get_stock` / `get_index` / `daily_kline` 触发。正在运行的
  `server.py` **不需要重启**就能用上新转出的交易日。
  验证：`scripts/verify_reload.py`。
- **断点续跑**：manifest 只在某交易日完整写完后才更新；重跑前会清掉该日旧分片，
  避免中断残留被读到。
- **构建锁 `_meta/.build.lock`**：同一 root 只允许一个转换进程。第二个进程会直接
  拒绝启动并打印锁文件年龄；超过 30 分钟的锁视为残留可自动接管。
  这一条是踩过坑加上的——两个转换进程同时写一个 root 会互相删分片、互相覆盖
  manifest。
- **看护器 `scripts/convert_all.py`**：逐日调用 builder，失败自动重试，带时间戳日志。

```powershell
# 推荐：看护器 + 绝对路径临时目录
python hfq/scripts/convert_all.py --root D:\data-lv2 `
    --temp C:\Users\david\dev\finance\hfq\cache\_build --retries 3
```

> **监控方式**：builder 每 4 个分片打一行 `进度 分片 k/36`，约 30–60 秒一条。
> 判断「是否在跑」看**日志的 mtime**，不要用 `Get-Process`——在沙箱里以扩权方式
> 启动的后台任务，其子进程在其他会话中，`Get-Process python` **看不到它们**，
> 据此判断"进程已死"会严重误判（教训）。

**安全设计：渐进迁移不丢数据。** `DATES` 取 Parquet 与 7z 归档的**并集**，
`_load_parquet` 失败即逐日回退到原路径。所以只转了一部分交易日时，其余交易日照旧
可用；`--codes` 子集构建的交易日会被标记 `partial`，清单与日线自动回退到归档口径，
不会隐藏未转换的标的。

### 5.3 延迟：结论取决于 Parquet 放在哪块盘

同一批文件（36 分片 × 256 只，`20260901`，5 只分位样本，中位数）在两块盘上差别很大：

| 路径 | 首次访问 |
|---|---|
| 旧：7z 抽取 + CSV 解析 | 0.51–0.535 s |
| 新：Parquet 放在 **C:**（本地快盘，**当前配置**） | **0.206–0.244 s**（快约 2.1x） |
| 新：Parquet 放在 **D:**（慢盘） | **1.148 s**（**比旧路径慢 2.1x**） |

所以最终把 **Parquet 放在 C:**、把 **7z 归档挪到 D:**——归档只在 Parquet 缺失时才读，
放在慢盘上不影响日常使用。

`scripts/bench_compare.py` 在 D: 上的明细（`20260921`）：

| 标的 | 事件数 | 旧冷 | 旧热(`bin`) | 新(Parquet) |
|---|---|---|---|---|
| `000001.SZ` | 229,248 | 1.468 s | 0.699 s | 2.576 s |
| `300957.SZ` | 53,053 | 0.636 s | 0.240 s | 1.148 s |
| `600509.SH` | 31,382 | 0.589 s | 0.149 s | 1.684 s |
| `159118.SZ` | 5,652 | 0.397 s | 0.031 s | 0.176 s |
| `900948.SH` | 6,358 | 0.412 s | 0.080 s | 0.591 s |

耗时与事件数不成比例（3 万事件的 `600509.SH` 比 5 千事件的 `159118.SZ` 慢 10 倍），
说明瓶颈是**每次加载要打开 3 个 Parquet 文件并读 footer**，在慢盘上是纯寻道开销，
而不是解码数据量。

**结论：Parquet 的冷加载优势依赖底层盘。** 放在快盘上约 0.21–0.24 s；放在慢盘上
约 1.1 s（反而比旧路径慢）。当前配置已把 Parquet 放在 C:。

> 如果 7z 归档所在的盘很慢，**回退路径**（`ensure_extracted`）也会变慢——但只有在
> Parquet 缺失或某标的未收录时才会走到它，59 天全量转换后基本不会触发。

### 5.5 源数据里的异常与处置

全量扫描（59 天全列）只命中 4 处价格越界，逐条核对原始 CSV 后确认**都是厂商写入
的真实值**，迁移忠实保留，不是转换错误：

| 现象 | 位置 | 旧实现表现 | 处置 |
|---|---|---|---|
| 无符号回绕的委托价 `2^64 - n` | `20260731` 等，7 只 | 解析成 `1.84e15` 元，`_encode_stock` 的 `array("i")` **OverflowError → 该股永久不可读** | 按二补码还原为 `-1.00` 元 |
| **带负号**的委托价（真实负数） | `20260706/07/08/10`，`001248.SZ`/`301583.SZ`，最低 `-210,420.73` 元 | 正常（值在 int32 内） | 原样保留 |
| 极端正价格 | `20260812/301717.SZ` 委托价 `1 亿元/股` | 正常 | 原样保留 |
| 负的当日成交额 `-2147483648`（INT32_MIN） | `20260706`，`688362.SH`/`688372.SH`；`20260707` 已修复 | 正常 | 见 7.9：这是**导出端**把累计成交额写爆 int32 的产物，重导的 `20260707` 已无此问题 |
| 代码区间 `2428xx–2448xx` 在某些交易日整体不存在 | 如 `20260807`/`20260814` | — | 该分片不写文件（正确行为） |

第一类**不是行为差异，而是修复了旧实现的一个真 bug**：旧代码把价格塞进
`array.array("i")`（int32），任何超 int32 的值都会让 `StockData()` 直接抛异常，
而 `_save_binary` 只捕获 `OSError`，异常一路冒到 HTTP 层变成 500。实测
`20260731` 的 7 只哨兵股票在旧实现下**全部崩溃**，新实现全部可读。

扫描的判据因此分两层：**结构性损坏**（数量为负、超出 int64 可表示范围等）报错；
**极端但真实的源数据**走"观测"通道单独打印极值区间，不阻断验收。

> 关于"全量扫描的最终结论"：`scan_anomalies.py` 在 59 天全列上只报过 4 处
> `orders.price`（即上表第二、三类）。这 4 处逐条与原始 CSV 核对后确认是源数据，
> 于是把价格界从 ±1e14 放宽到 ±1e15（放宽只会**减少**告警），并对这 4 个交易日
> 重跑得到 `异常 0`。因此全量口径下异常为 0 是由上述两步共同确立的，
> 不存在未检查的列或日期。

## 6. 怎么用

### 构建

```powershell
# 全量（59 个交易日，按月分区）
python hfq/scripts/build_parquet.py --all --freq month          # 默认写 hfq/data-parquet

# 按周分区
python hfq/scripts/build_parquet.py --all --freq week --root hfq/data-parquet-week

# 指定交易日 / 指定标的（子集构建会标记 partial）
python hfq/scripts/build_parquet.py --dates 20260901 20260902
python hfq/scripts/build_parquet.py --dates 20260901 --codes 001301.SZ 600967.SH

# 断点续跑：已完成的交易日自动跳过；崩溃后复用已解压临时目录
python hfq/scripts/build_parquet.py --all --reuse-temp
```

> `--temp` 一定要放在**快的盘**上：单日解压 41–52 GB，且解析阶段要把它们再读一遍。
> 本机实测临时目录放 D: 会让单日从 605 s 涨到 1295 s（见下节）。默认的
> `hfq/cache/_build`（C:）是对的。

单日成本（实测）：解压 108–123 s + 解析/写盘 约 500 s ≈ **10 分钟/日**，
56 日约 **9.5 小时**、产出约 **277 GB**。

> ⚠️ 磁盘：Parquet（278 GB）现在放在 `C:` 上，7z 归档（318 GB）在 `D:\data-lv2`。
> 转换时临时目录用默认的 `hfq/cache/_build`（与 Parquet 同盘，快）。

### 读取

无需改调用方 —— `data.py` 按顺序自动探测数据集位置，用第一个能打开的：

1. 环境变量 `HFQ_PARQUET_DIR`（显式指定优先）
2. 仓库内 `hfq/data-parquet/` —— **当前实际位置（C: 快盘）**

7z 归档目录同理：`HFQ_ARCHIVE_DIR` → 仓库内 `hfq/data-lv2/` → `D:\data-lv2`（**当前实际位置**）。
两者可以分开放在不同盘上。

都不存在时完全回退到 7z 路径。

```powershell
$env:HFQ_PARQUET_DIR = "D:\somewhere\data-parquet"   # 可选：显式指定
$env:HFQ_ARCHIVE_DIR = "E:\lv2-7z"                   # 可选：归档另放
python hfq/server.py
```

### 慢盘的代价：为什么 Parquet 最终放在 C:

原先测到的「D: 读 3264 MB/s」是**页缓存虚高**，不能作为介质速度的依据。用
`fsync` 落盘的写入测试才是真实能力（`scripts/bench_disk.py` + 下面的写测试）：

| 指标 | C: | D: | 比值 |
|---|---|---|---|
| 大文件顺序写（512 MB, fsync） | 1877 MB/s | **82 MB/s** | D: 慢 23x |
| 小文件创建（1500 × 20 KB） | 3316 个/s | **457 个/s** | D: 慢 7x |
| 7z 解压 1 天（41–43 GB） | **95–123 s** | 331–358 s | D: 慢 3.5x |
| 解析当天（读临时 CSV） | **255–270 s** | 689–726 s | D: 慢 2.7x |
| 单日转换总耗时 | **605–675 s** | 1290–1305 s | D: 慢 2.1x |

结论：D: 明显是比 C: 慢的卷（像是机械盘或限速卷），随机/小文件操作尤其吃亏。

因此最终采用的配置是——**临时解压留在 C:，只有最终 Parquet 写 D:**：

```powershell
python scripts/build_parquet.py --all --reuse-temp
```

- 临时目录每天 41–52 GB，逐日删除，转换结束后完全释放（转换期间 C: 峰值占用约 52 GB）；
- 每天只有约 5 GB 的 Parquet 要落到 D:，按 82 MB/s 约 60–90 s，不再是瓶颈；
- 单日总耗时回到 **605 s** 左右。

> 运行时读取仍会从 D: 取 Parquet。由于上面两次 C: 上的
> `get_stock` 延迟（0.235 s）是在 C: 上测的，D: 上的真实冷读延迟需在转换完成、
> 缓存冷却后重测。若明显变差，可把 `--root` 换到本地 SSD 盘。

磁盘余量：D: 约 12.7 TB；C: 在转换启动时约 419 GB 可用（足以放下 **278 GB** 数据集，
但你要的是不占用系统盘，故仍放 D:）。

## 7. 扩到 2026-01~09：整份重建（2026-10-28）

前面的结论都建立在 59 个交易日（2026-06-30 ~ 2026-09-21）上。这次把 NAS 上
2026-01 ~ 2026-06 的归档也拉了回来，数据集扩到 **175 个交易日**。扩的过程里踩了
四个坑，每个都会静默出错或直接毁数据，记在这里。

### 7.1 为什么必须整份重建：universe 一改，分片下标全错

`shard_of(code)` 是 `universe` 有序表里的 `下标 // 256`。新月份带来了现有数据集
里没有的代码（退市股、以及 2026-01~06 才有的标），实测每个交易日 **142~162 只**
不在旧 universe 里：

```
20260105: 当日 7619 只  不在 universe 的 154 只
20260112: 当日 7651 只  不在 universe 的 162 只
```

`universe` 从 9,143 涨到 **11,191**，分片从 36 变 **44**。这会让所有代码的 shard
下标整体位移 —— 旧分片文件里的 `code` 列与新 manifest 的映射对不上，读出来就是串码。
所以不能「只转新增的 116 天」，必须 175 天全量重建。

> 代价：7.6 小时的并行转换（串行要 35 小时）。收益：一份自洽的数据集，而且新 universe
> 把退市股也收进来了，这对回测很重要（否则就是幸存者偏差）。

### 7.2 新归档是「平铺」结构，按 `parts[1]` 取代码会得到 0 只

```
旧（2026-06-30 起）:  20260921/000001.SZ/行情.csv
新（2026-01~06）  :  000001.SZ/行情.csv
```

按 `filename.split("/")[1]` 取代码在平铺归档上拿不到任何标的，**而且不报错**，
只是那一天「没有数据」。统一走 `hfq/app/archive_layout.py: code_of()`（扫成员名里
形如 `000001.SZ` 的段），`build_parquet.py` / `app/data.py` / `ambush/strategy.py`
三处都已经改掉。

### 7.3 新归档每行少一个尾部空列

| 文件 | 旧列宽 | 新列宽 |
|---|---|---|
| 逐笔委托.csv | 11 | 10 |
| 逐笔成交.csv | 13 | 12 |
| 行情.csv | 67 | 66 |

少的是行尾那个空列（旧行以 `,` 结尾）。解析用的是列下标（委托 ≤9、成交 ≤11、
行情 ≤60），两种布局都覆盖，但 pyarrow 的 `column_names` 必须与行字段数一致，
否则会因 "expected N columns" 整体回退到 pandas（慢 16 倍）。现在按数据段首行
动态探测宽度（`_width_of`），两种布局都走 arrow 快路径。

### 7.4 py7zr 会内存爆炸，把整机打挂

用 py7zr 1.1.3 `extractall` 解这些 3 万成员的单块归档时，它把解压结果整体堆在内存里：

```
python.exe (54716) 虚拟内存 110~117 GB  →  提交上限 63 GB 耗尽
9:29 dwm.exe 崩溃 (0xc000012d)          →  9:44 整机硬卡死
10:20 非正常关机后重启（事件 6008）
```

这台机器 32 GB 物理内存 + 32 GB 页面文件，提交上限只有 63 GB。定向抽取也会偶发
`Bad7zFile: Specified path is bad`（换个目标目录就复现），它的路径校验在 Windows 上
对 realpath 与父目录前缀的比对并不稳。

现在统一用 **7z 命令行**：流式写盘、内存有界（解 45 GB 提交内存只涨几百 MB），
而且快一倍（221 s vs py7zr 的 ~450 s）。找不到 7z 时才回退 py7zr 的定向抽取。

### 7.5 并行构建：4 进程，内存看门狗

单日 12 分钟 × 175 天串行要 35 小时，而瓶颈不是 CPU（24 核只用了 17%）而是
D: 这块 7200 转 SATA 盘（读写混跑只有 ~40 MB/s）。`scripts/build_parallel.py`
把交易日切成互不相交的分组，4 个进程同时转：

| 机制 | 作用 |
|---|---|
| `--slots N` 槽位锁 | 同一 root 最多 N 个进程，防误起第二个 |
| `merge_manifest` 短临界区 | 占锁 → 重读磁盘最新 manifest → 合并 → 原子替换，避免整份覆盖 |
| 静态分组 | 每个进程只碰自己那批交易日，分片目录天然不冲突 |
| 内存看门狗 | 提交内存超阈值就杀掉全部 worker，防止再次整机卡死 |

实测 175 天 **7.6 小时**（19 天/小时），单日 263~280 s 解压 + 222~228 s 解析。

### 7.9 `20260707` 是个残缺导出，已换档重建

NAS 上还有一份 `20260707(1).7z`（5.69 GB vs 原档 4.41 GB）。核对成员清单：

A 股数量一致，但**同一只 A 股的行情内容不一样**：原档把累计成交额写成了
`-2147483648`（INT32_MIN），重导档是正确的 `2,147,655,143` 这类真实值。实测
`20260707/600519.SH/行情.csv` 原档有 1,672 行被写坏，重导档 0 行。

所以 5.5 里那条「源数据本来就有 INT32_MIN」的判断需要修正：**它是导出端的 bug**，
至少 20260707 有干净的替代版本。处理方式：

1. 原档移到 `D:\data-lv2\_extra\20260707.partial.7z` 留证；
2. 用重导档替换 `D:\data-lv2\20260707.7z`；
